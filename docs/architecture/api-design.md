# API 设计

## 双服务架构

async-scheduler 对外暴露两个独立的 HTTP 服务：

| 服务 | 端口 | 目标用户 | 安装包 |
|------|------|----------|--------|
| **Task API** | 8001 | 业务方 / 调用方服务 | `async-scheduler-task-api` |
| **Ops API** | 8000 | 运维人员 / 管理员 | `async-scheduler-ops-api` |

两个服务独立部署，可以：
- **独立扩缩容**：按各自负载独立调整副本数
- **差异化网络暴露**：Task API 对外开放，Ops API 仅限内网
- **独立鉴权策略**：为业务用户和运维人员配置不同的认证方式

## Task API 设计原则

- REST over HTTP/1.1，请求与响应均为 JSON
- 所有任务操作基于 `task_id` 保证幂等性
- 默认异步模式：提交立即返回，通过轮询或回调获取结果
- 支持 `callback_url`：任务完成后主动推送结果

## Ops API 设计原则

- 提供所有配置实体的完整 CRUD 操作（集群、节点、DAG、capability、租户）
- 以读操作为主：列表接口支持游标分页与丰富的过滤条件
- 写操作会进行业务规则校验（如 capability 名称唯一性）
